## 1. 先理解A、B、C在比較什麼

A與B比較的是「LLM解說放在哪裡」；C比較的是「視覺層要不要增加YOLO」。C不是第三種LLM部署方式。

| 方案 | 定義 | 本階段決定 |
|---|---|---|
| A | 雲端MediaPipe／規則評分＋雲端LLM解說 | **目前預設方案** |
| B | 地端MediaPipe／規則評分＋地端Gemma 4解說 | 技術可行，保留為離線／隱私備案 |
| C | MediaPipe保留，再選擇性增加YOLO看球拍、羽球或落點 | 短期先用MediaPipe；官方YOLO26n可作選配增強 |

## 2. A與B的階段性結論

### B不是不能用

Gemma 4加入Ollama原生Schema後，可以穩定產生指定的五個欄位，因此不能再說Gemma 4格式很差，也不需要只為固定欄位導入LangChain。

本機安全輸出流程為：

`Gemma 4＋原生Schema → Python內容檢查 → 不合格時使用固定模板`

### B的實測結果

| 項目 | 結果 |
|---|---:|
| 共用案例 | 28 |
| 加Schema後欄位型別正確 | 28/28 |
| 改善重點有原始依據 | 67.9% |
| 優點有原始依據 | 53.6% |
| Gemma原始輸出十項全部通過 | 13/28 |
| 需要固定模板接手 | 15/28 |
| B1 p50／p95 | 1.45／2.13秒 |
| 模型檔 | 約7.2 GB |
| 常駐記憶體 | 約6.7–7.0 GB |

設備判斷：8 GB RAM不建議；16 GB為最低建議；24 GB較適合開發與實驗。單一地端runner在1、2、4個同時請求下，總吞吐約維持0.48 requests/s，請求增加時主要是排隊。

單人MVP不需要租VM。本機M5 Pro可執行；若改租VM，就會變成自行維護的雲端模型。先前價格只作情境估算：CPU VM約US$141.79／月，L4 GPU VM約US$515.99／月，並非租機實測或正式預算。

### 為什麼仍選A

A的同條件28案例原始輸出十項檢查為28/28，不需要像B一樣讓15筆改用固定模板；也不要求每位使用者安裝約7 GB模型、Ollama與本機guardrail。版本、提示詞、Schema與回滾可集中管理。

因此正確結論是：

> B技術上可行，適合離線或隱私情境；但目前預設仍選A，原因是原始內容依據較穩定、終端設備要求較低、維護較集中。

## 3. C：MediaPipe與MediaPipe＋YOLO26n的差異

MediaPipe看「人體怎麼動」，YOLO26n補看「球拍在哪裡」。兩者是互補，不是互相取代。

| 能力 | MediaPipe | MediaPipe＋YOLO26n |
|---|---|---|
| 人體關節、手腕、手肘、肩膀 | 有 | 有 |
| 動作角度與規則評分 | 有 | 有 |
| 直接看見球拍 | 沒有 | 有球拍候選框 |
| 持拍手方式 | 依手腕動作推測 | 將球拍框與左右手腕配對 |
| 成本 | 較低 | 增加模型、記憶體與推論時間 |

在目前6段、全部為右手持拍的影片中：

| 結果 | MediaPipe | MediaPipe＋官方YOLO26n |
|---|---:|---:|
| 能做出判斷 | 5/6 | 6/6 |
| 符合人工右手答案 | 2/6 | 5/6 |

這只能稱為「目前6個右手案例的一致結果」，不能稱為正式準確率，因為沒有左手案例、案例也太少。

短期MVP不需要為持拍手特別自訓模型：MediaPipe繼續負責關節姿態與規則評分，持拍手可由規則搭配使用者確認。如果希望增加自動球拍證據，可以先加入官方預訓練YOLO26n。

## 4. 小型監督式微調做了什麼

本輪做的是「AI輔助預標註的監督式微調」，不是從零訓練：

1. 從6段真實右手影片抽出72張影格。
2. YOLO26s與YOLO26m同時高信心同意時，產生 provisional球拍框。
3. 嚴格篩選後留下34張。
4. 按完整來源影片切成train／validation／test＝19／6／9，沒有來源影片跨組。
5. 先做5 epochs短測，再從官方YOLO26n重新做40 epochs正式微調。
6. 用未參與訓練的test影片比較官方模型與微調模型。

簡單說，訓練就是：

`圖片＋球拍答案框 → 模型猜球拍 → 比較答案 → 修改參數 → 重複40輪`

### 微調結果

| test指標 | 官方預訓練YOLO26n | 40 epochs微調 |
|---|---:|---:|
| Precision | **80.00%** | 66.67% |
| Recall | **44.44%** | 22.22% |
| F1 | **57.14%** | 33.33% |
| AP50 | **67.46%** | 30.76% |
| AP50-95 | **32.06%** | 8.82% |
| 找到球拍的test影格 | **5/9** | 3/9 |

訓練流程成功執行，但模型效果失敗，因此不採用微調權重。主要原因是train只有19張、答案框不是人工ground truth、沒有負樣本、沒有左手案例，且人物與場景多樣性不足。

正確說法是：

> 我完成了YOLO26n的監督式微調經驗，但少量AI預標註沒有讓模型變好。訓練流程成功，不代表模型效果成功。

## 5. 500張資料應該怎麼說

不能保證「累積500張就一定提高正確率」。比較有依據的說法是：

> 如果未來能累積至少500張經過人工確認，並包含不同球員、左右手、拍攝角度、場館、遮擋、模糊與負樣本的圖片，模型會比目前更有機會提升泛化能力；是否真的改善，仍要以鎖定的獨立test set驗證。

相鄰的1,000張同一影片畫面，不一定比500張多人物、多場景且標註正確的圖片更有價值。

## 6. 本階段正式決策

| 面向 | 決定 |
|---|---|
| LLM解說層 | A作預設 |
| 地端Gemma 4 | B作離線／隱私備案 |
| 人體姿態與規則評分 | 保留MediaPipe |
| 短期持拍手 | 規則＋使用者確認 |
| 自動球拍證據 | 可選擇加入官方YOLO26n |
| 本輪自訓YOLO26n | 不採用 |
| 未來較值得自訓的方向 | 羽球偵測、球路追蹤與落點分析 |

羽球落點不能只靠YOLO。若未來執行，需要：羽球專用偵測、跨影格追蹤、落地事件判定、球場線／角點與homography座標校正。現成YOLO26n沒有專門的羽球類別，因此這類任務比目前單純持拍手更有自行蒐集資料與訓練的理由。

## 7. 報告時可以直接說的版本

> 本研究分成兩個面向。A與B比較LLM解說要放在雲端還是地端；C比較視覺層只使用MediaPipe，還是加入YOLO。B方案證明Gemma 4加入原生Schema、驗證與固定模板後可以在本機使用，但需要約7 GB模型與至少16 GB記憶體，28個案例中也有15個需要固定模板接手，因此本階段仍選A作為預設，B保留作離線或隱私備案。視覺層方面，MediaPipe已足以處理人體關節與規則評分；官方YOLO26n可以補充球拍證據，但目前只有6段右手案例，因此不能宣稱正式準確率。小型YOLO26n微調雖完成40個epochs，但因訓練資料只有19張且為AI預標註，測試結果反而退步，所以不採用自訓權重。短期MVP維持MediaPipe，持拍手由規則或使用者確認；未來真正值得自訓的方向是羽球、球路與落點分析。

## 8. 不能寫錯的地方

- 不可寫「MediaPipe持拍手準確率80%」。本輪6個右手案例只符合2個。
- 不可寫「MediaPipe＋YOLO26n準確率90%以上」。本輪是5/6右手案例一致，而且不是平衡準確率。
- 不可寫「自訓YOLO成功提高效果」。正確說法是訓練流程完成，但test結果退步。
- 不可寫「500張一定會改善」。只能說多樣、人工確認的500張更有機會改善，仍需test驗證。
- 不可寫「A已正式上線」。目前完成的是隔離LLM實測，完整影片上傳、Cloud Run、正式帳單與人工教練盲評仍屬未來工作。
- 不可把C寫成A／B以外的第三種LLM方案。
