# A/B/C 實驗口頭報告稿（從零開始版）

## 30 秒版本

我們把問題拆成兩組。第一組 A 雲端 LLM vs B 地端 Gemma 4：B 加完整 Schema 後格式能到 100%，但原始十項全過只有 13/28，另有 15/28 要固定模板接手，再加上 7.2 GB 模型與至少 16 GB RAM，所以仍選 A 作預設。第二組是 MediaPipe vs MediaPipe＋YOLO：預訓練 YOLO26n 在 6 段右手影片表現最好；我又真的用 34 張 AI 預標註做小型微調，但保留影片 AP50 反而從 67.5% 降到 30.8%。因此我完成了訓練經驗，也用數據證明目前資料不夠，MVP 仍用 MediaPipe，不採用這個自訓權重。

## 3–5 分鐘版本

### 1. 問題是什麼

我想把一段羽球影片轉成兩種東西：第一是有根據的動作分數；第二是一般人看得懂的說明。

這兩件事不能混在一起。分數要由固定的 MediaPipe 骨架與規則引擎產生；LLM 只負責把結果說成人話，不能自己改分數。

### 2. A、B、C 是什麼

A 像中央廚房。影片送到雲端，同一套 MediaPipe 和 LLM 處理完，再把報告送回來。好處是使用者不用準備大模型，系統也能集中更新。

B 像每個人家裡都裝一套廚房。影片和文字模型都留在本機，隱私和離線能力好，但每台電腦都要有足夠的記憶體、模型檔和維護能力。

C 像替 MediaPipe 加一位物件球探。MediaPipe 繼續看人的肩膀、手肘、手腕；YOLO 補看球拍、羽球、球路或落點。C 能加在 A 或 B 前面，不是第三種 LLM 部署方式。

### 3. 共同的 MediaPipe 基準

我先拿 16.217 秒的真實 PoC 影片跑三次。平均 5.365 秒完成，大約 127 FPS，峰值記憶體 368.94 MB，而且三次分數都是 87。

這告訴我：現有評分核心可以沿用，不需要讓 LLM 或 YOLO 重新發明分數。

### 4. B 實驗告訴我什麼

我把三份不同的動作報告交給本機 Gemma 4，共測 GPU 6 筆、CPU-only 3 筆。兩種模式的 JSON 都 100% 可解析，代表功能做得到。

但代價是模型檔約 7.2 GB，常駐約 6.7–7.0 GB。在 24 GB 的 M5 Pro 上，GPU 暖機後平均約 1.91 秒，CPU-only 約 3.81 秒。因此 8 GB 不建議，16 GB 是最低建議，24 GB 比較適合實驗。

我也測了同時送入兩筆。單筆吞吐是 0.5168 requests/s；兩筆同時送入後，總吞吐仍只有 0.5154 requests/s，其中一筆約 1.92 秒完成，另一筆要等到約 3.9 秒。也就是功能雖然成功，但單一地端模型主要是在排隊，不能因為記憶體夠就假設多人速度會加倍。

接著我把測試擴大成 28 份：19 份是真的由現有影片跑出來，9 份是明確標示的壓力測試 JSON。B0 只有 Prompt 與 JSON mode，欄位型別是 0%；B1 把完整 Schema 傳給 Ollama 後，型別立刻變 100%，p50/p95 是 1.45/2.13 秒。這證明格式問題是整合方式。但 priority grounding 67.9%、strength grounding 53.6%，原始十項全過 13/28。B2 加入驗證與固定模板後，15 筆 fallback，最終 28/28。這告訴我 Schema 管格式，guardrail 管產品安全，兩者不能冒充模型內容品質。

並行測試擴大到 1、2、4 個請求後，p95 等待約是 2.07、4.14、8.30 秒，但總吞吐一直約 0.48 requests/s。單一 runner 不是同時完成四筆，而是讓四筆排隊。

如果為了 B 去租 VM，CPU 16 GB 的參考情境約 US$141.79/月，L4 GPU 情境約 US$515.99/月，而且還要自己管理模型。這時它已經不是純地端方案了。

### 5. MediaPipe＋YOLO 實驗告訴我什麼

我先用 YOLOv12 作者程式做 16 張合成圖、1 epoch 的流程測試。mAP、precision、recall 都是 0；它只證明訓練程式能跑，不能代表 YOLO 不適合羽球。

接著比較 YOLO11n、YOLO12n 與 YOLO26n。資料是 6 段真實發球影片、每段 12 張，共 72 張；YOLO 找球拍，MediaPipe 提供左右手腕，再用相同規則配對。

MediaPipe 單獨在全部 6 案例符合右手答案 2 例；加 YOLO11n 是 3 例；加 YOLO12n 也是 3 例；加 YOLO26n 是 5 例，而且 YOLO26n 6 例都能判定。YOLO12n 雖然比 YOLO11n 多看到球拍候選，但沒有改善案例答案，p50 也最慢。這讓我選 YOLO26n 當下一輪微調候選。但 6 段全是右手、沒有人工球拍框，所以不能稱為左右手準確率，也不能報 mAP。

我再把 YOLO26 的 n、s、m 各跑三輪。三者都能判定 6/6，但 n 符合 5/6，s 與 m 都只有 4/6；p95 分別是 18.9、22.4、45.4 ms，權重是 5.54、20.42、44.26 MB。s、m 確實看到更多球拍，但在其中一案增加錯側票，所以「更大」不等於「持拍手更準」。這三個模型都在本機免費執行，沒有每次使用費，差別是空間、等待時間與電力。

最後我真的做了一次 YOLO26n 微調。72 張來源中，只保留 26s 和 26m 都高信心同意的 34 張，再用完整影片切成 19 張 train、6 張 validation、9 張 test。5 epochs 短測成功後，正式跑 40 epochs、約 97.5 秒。但在保留影片上，AP50 從原始模型 67.5% 降到 30.8%，recall 從 44.4% 降到 22.2%。原因是資料太少、標籤不是人工 ground truth、沒有負樣本且全是右手。這證明 training loss 下降不等於產品變準；目前不採用微調權重。

### 6. 為什麼選 A

我選 A，不是因為 Gemma 做不到。B 已證明用 Ollama Schema + Python guardrail 就能做成安全輸出，而且本輪不需要 LangChain。但 B 原始內容仍有 53.6% 要 fallback，一般使用者還要下載 7 GB 模型；A 的原始輸出較穩，版本、提示詞、Schema 和回滾也能集中管理。

所以我的結論是：解說層現階段選 A，B 保留作離線或隱私特殊情境；視覺層保留 MediaPipe，YOLO26n 作為球拍、球路與落點的中長期增強候選。

同時我要誠實說明：A 的 LLM API 已在隔離 Free tier 專案完成，但尚未部署完整影片上傳與 Cloud Run，也沒有正式帳單或人工教練盲評。

## 常見追問與回答

### Q1：既然 B 的成功率是 100%，為什麼不選 B？

Gemma 加 Schema 後型別已是 100%，所以不能再說它格式很差。真正差異是原始內容只有 13/28 十項全過，另 15 筆要 fallback；每個執行端還要有約 7 GB 模型、至少 16 GB RAM，並維護 Ollama、Schema、驗證與模型版本。B 適合離線/隱私情境，但目前仍不是最低維護成本的預設方案。

### Q2：A 有真的跑雲端嗎？

有，但只跑了隔離專案的 LLM 解說層：28/28 完成，p50 1.6191 秒、p95 2.4000 秒。沒有上傳影片，也沒有部署 Cloud Run。正確說法是「A 的 LLM 已實測，完整雲端端到端尚未實測」。

### Q3：費用到底是多少？

28 筆 API 的實際 token usage 套 paid-tier 單價等值為 US$0.0121284，但專案顯示 Free tier，所以這不是實際帳單。10,000 次完整流程約 US$7.2307 仍只是 LLM 加簡化 Cloud Run CPU/RAM 的情境，沒有 Storage、網路、DB、logging、重試和稅，不可當正式預算。

### Q4：舊 C 的 mAP 是 0，是不是代表 YOLO 不適合？

不是。那次只有 16 張合成圖片且只訓練 1 epoch，只是管線測試。新的 6 段真實影片基準已顯示 YOLO26n 能補球拍證據；但沒有人工框，所以仍不能宣稱 mAP。

### Q5：YOLO 能不能直接做落點？

不能只靠 YOLO。YOLO 可以找羽球，還需要把連續影格串成軌跡、辨識落地時間、辨識球場角點，最後把影像座標換成球場座標。

### Q6：為什麼 C 先做持拍手？

球拍比高速羽球大、比較容易標，也能立刻和現有 MediaPipe 左右手腕融合，所以最容易得到第一個有意義的增強結果。

### Q7：Gemma 可以改分數嗎？

不可以。分數是 MediaPipe 與規則引擎的版本化結果。Gemma 或雲端 LLM 只能解說；若 LLM 失敗，固定分數仍然存在。

### Q8：Gemma 4 已經是地端模型的最後定案嗎？

它已定案為 B 的可行 baseline，因為只有它完整跑過 28 案例、Schema、guardrail、CPU/GPU 與並行測試；但還不是「最佳地端模型」定案。若排除中國模型，下一輪最值得用同一份考卷測的是法國 Mistral AI 的 Ministral 3 8B、美國 IBM 的 Granite 4.1 8B，以及美國 Microsoft 的 Phi-4-mini。沒有同條件實測前不能直接宣布誰取代 Gemma 4。

### Q9：你真的有訓練模型嗎？為什麼訓練後更差？

有。先跑 5 epochs 短測，再從官方 YOLO26n 重新跑 40 epochs 正式微調，並保存最佳權重與 SHA-256。變差的核心不是程式沒跑，而是 train 只有 19 張，標籤由其他 YOLO 共識產生、沒有負樣本、沒有左手。模型變得更會配合這幾段影片，卻沒有更會處理另一段影片，這就是小資料泛化不足。
