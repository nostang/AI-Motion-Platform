# A/B/C 實驗口頭報告稿（從零開始版）

## 30 秒版本

我們要做的是：把羽球影片變成動作分數和人看得懂的建議。我比較三種作法。A 把 MediaPipe 與 LLM 放在雲端；B 把 MediaPipe 與 Gemma 4 放在使用者本機；C 自己訓練 YOLOv12。實驗顯示，既有 MediaPipe 核心已經穩定；B 雖然能成功解說，但模型約 7.2 GB，建議至少 16 GB RAM；C 的訓練流程能跑，但這次小資料模型的 mAP、precision、recall 都是 0，還沒有可用準確度。因此目前選 A：保留穩定分數、把大模型和更新集中在雲端，不要求每個使用者有高階電腦。但 A 的真正雲端延遲、品質和帳單仍需在隔離測試環境補驗。

## 3–5 分鐘版本

### 1. 問題是什麼

我想把一段羽球影片轉成兩種東西：第一是有根據的動作分數；第二是一般人看得懂的說明。

這兩件事不能混在一起。分數要由固定的 MediaPipe 骨架與規則引擎產生；LLM 只負責把結果說成人話，不能自己改分數。

### 2. A、B、C 是什麼

A 像中央廚房。影片送到雲端，同一套 MediaPipe 和 LLM 處理完，再把報告送回來。好處是使用者不用準備大模型，系統也能集中更新。

B 像每個人家裡都裝一套廚房。影片和文字模型都留在本機，隱私和離線能力好，但每台電腦都要有足夠的記憶體、模型檔和維護能力。

C 像自己訓練一位專門找羽球的球探。它可能看見 MediaPipe 看不到的球拍、羽球、球路或落點，但是要先蒐集與標註真實資料，再訓練和驗證。

### 3. 共同的 MediaPipe 基準

我先拿 16.217 秒的真實 PoC 影片跑三次。平均 5.365 秒完成，大約 127 FPS，峰值記憶體 368.94 MB，而且三次分數都是 87。

這告訴我：現有評分核心可以沿用，不需要讓 LLM 或 YOLO 重新發明分數。

### 4. B 實驗告訴我什麼

我把三份不同的動作報告交給本機 Gemma 4，共測 GPU 6 筆、CPU-only 3 筆。兩種模式的 JSON 都 100% 可解析，代表功能做得到。

但代價是模型檔約 7.2 GB，常駐約 6.7–7.0 GB。在 24 GB 的 M5 Pro 上，GPU 暖機後平均約 1.91 秒，CPU-only 約 3.81 秒。因此 8 GB 不建議，16 GB 是最低建議，24 GB 比較適合實驗。

我也測了同時送入兩筆。單筆吞吐是 0.5168 requests/s；兩筆同時送入後，總吞吐仍只有 0.5154 requests/s，其中一筆約 1.92 秒完成，另一筆要等到約 3.9 秒。也就是功能雖然成功，但單一地端模型主要是在排隊，不能因為記憶體夠就假設多人速度會加倍。

如果為了 B 去租 VM，CPU 16 GB 的參考情境約 US$141.79/月，L4 GPU 情境約 US$515.99/月，而且還要自己管理模型。這時它已經不是純地端方案了。

### 5. C 實驗告訴我什麼

我使用 YOLOv12 作者官方程式，建立 12 張訓練圖和 4 張驗證圖，跑 1 epoch。訓練花 26.97 秒，模型約 5.38 MB，推論本身很快。

可是 mAP、precision、recall 全部是 0。這不是說 YOLO 永遠做不到，而是證明「訓練程式跑完」和「模型真的會看羽球」是兩件不同的事。

C 下一步應該先做持拍手，再做羽球路徑，最後才做落點。持拍手要標球拍框並和 MediaPipe 手腕配對；球路徑要高 FPS 影片與逐幀羽球標註；落點還要做球場座標校正和落地事件判定。

### 6. 為什麼選 A

我不是因為 A 已經全部測完才選它，而是因為 A 最符合目前產品條件：它可以直接沿用已穩定的 MediaPipe 分數；一般使用者不用下載 7 GB 模型；版本、提示詞和回滾可以集中管理；C 尚未有真實羽球模型品質。

所以我的結論是：現階段選 A，B 保留作離線或隱私特殊情境，C 作為球拍、球路與落點的中長期增強研究。

同時我要誠實說明：A 的雲端 LLM、網路延遲、冷啟動和真實帳單這次沒有實測，因為本輪禁止建立或呼叫雲端資源。正式決策前要在完全隔離的測試專案補做。

## 常見追問與回答

### Q1：既然 B 的成功率是 100%，為什麼不選 B？

100% 指這 9 次輸出都能解析，不代表所有內容永遠正確。更重要的是，每個使用者端都要有約 7 GB 模型與至少 16 GB RAM，還要維護 Ollama 和模型版本。B 適合離線/隱私特例，不適合當預設大眾部署。

### Q2：A 沒有真的跑雲端，怎麼能選？

這次能證明的是 A 的核心 MediaPipe 可行、部署結構最符合條件、成本可建立透明公式；不能證明實際雲端延遲與品質。正確說法是「條件式選 A」，正式上線前必須在隔離雲端環境補驗。

### Q3：10,000 次只要 US$2.216，真的這麼便宜嗎？

不是完整帳單。它只包含一個簡化的 LLM token 與 Cloud Run CPU/RAM 情境，沒有 Storage、網路、DB、logging、重試和稅。這個數字用來比較成本結構，不可當正式預算。

### Q4：C 的 mAP 是 0，是不是代表 YOLO 不適合？

不是。資料只有 16 張合成圖片且只訓練 1 epoch，本來就不能代表羽球模型。零指標的意義是提醒我們：下一步必須投入真實標註資料，不能只看到模型檔產生就宣稱成功。

### Q5：YOLO 能不能直接做落點？

不能只靠 YOLO。YOLO 可以找羽球，還需要把連續影格串成軌跡、辨識落地時間、辨識球場角點，最後把影像座標換成球場座標。

### Q6：為什麼 C 先做持拍手？

球拍比高速羽球大、比較容易標，也能立刻和現有 MediaPipe 左右手腕融合，所以最容易得到第一個有意義的增強結果。

### Q7：Gemma 可以改分數嗎？

不可以。分數是 MediaPipe 與規則引擎的版本化結果。Gemma 或雲端 LLM 只能解說；若 LLM 失敗，固定分數仍然存在。
