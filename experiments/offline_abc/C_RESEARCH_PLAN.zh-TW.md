# C：MediaPipe＋YOLO 羽球視覺增強研究計畫

這份計畫把「在 MediaPipe 之外加上 YOLO」拆成三個可以驗證的小問題。YOLO 不取代 MediaPipe，也不取代 A/B 的 LLM；它只補足球拍、羽球與落點等物件資訊。數量與門檻是 **PoC 起始建議**，不是已實測結果，也不是產業通用保證。

## 已完成的第一輪：持拍手預訓練基準

Ultralytics 對穩定工作負載建議 YOLO11 或 YOLO26；為了同時回答 YOLO12 的差異，本輪以同為 nano 等級的 YOLO11n、YOLO12n、YOLO26n，搭配現有 MediaPipe 做公平比較；未使用專案資料微調。

- 資料：6 段真實發球影片，每段 12 張，共 72 張；人工答案全為右手。
- YOLO11n：4/6 可判定、3/6 與右手答案一致，p95 19.6 ms/frame。
- YOLO12n：5/6 可判定、3/6 與右手答案一致，p95 18.9 ms/frame。
- YOLO26n：6/6 可判定、5/6 與右手答案一致，p95 14.4 ms/frame。
- 結論：YOLO26n 作為下一輪主要微調候選，YOLO11n、YOLO12n 留作控制組。
- 限制：左手影片 0 段、人工球拍框 0 張，因此不是平衡準確率，也不能報 precision、recall 或 mAP。

完整方法、逐案結果與失敗分析見 [MediaPipe vs MediaPipe＋YOLO 比較報告](C_MP_YOLO_COMPARISON.zh-TW.md)。

## 已完成的第二輪：YOLO26 n／s／m 尺寸比較

以相同 6 段、72 張、1280 px、confidence 0.15 與 M5 Pro MPS，比較 YOLO26n、s、m；每個模型用獨立程序跑三輪。三個尺寸都能判定 6/6，但 26n 符合人工右手答案 5/6，26s、26m 都是 4/6。三輪合併 p95 分別為 18.9、22.4、45.4 ms/frame；權重分別為 5.54、20.42、44.26 MB。

這輪決定單人 MVP 繼續使用 YOLO26n。s、m 雖有較多球拍／手腕證據，R-SV-01 卻增加錯側票，因此不能用「模型比較大」代替任務實測。完整成本、逐案例與儀表板欄位見 [YOLO26 n／s／m 地端實測報告](C_YOLO26_SCALE_COMPARISON.zh-TW.md)。

## 已完成的第三輪：YOLO26n 小型微調經驗

為了真正走過一次訓練流程，本輪用 YOLO26s＋26m 的嚴格共識建立 34 張 provisional racket labels，依完整來源影片切成 train/val/test = 19/6/9；先跑 5 epochs 短測，再從官方 YOLO26n 重新跑 40 epochs 正式微調。

保留影片測試顯示微調沒有改善：AP50 從 67.46% 降到 30.76%，recall 從 44.44% 降到 22.22%。因此本輪只完成「訓練經驗與管線驗證」，不採用微調權重，也不改變 MediaPipe 優先的 MVP 決定。詳細資料、圖表與原因見 [YOLO26n 小型羽球拍微調報告](C_YOLO26N_FINETUNE_PILOT.zh-TW.md)。

## 先理解：YOLO 是找東西，不是自動懂羽球

YOLO 的基本工作像是在每張照片上畫框並說「這裡有球拍」「這裡有羽球」。它不知道人體動作好不好，也不知道畫面中的點對應球場哪一個公分位置。持拍手、球路與落點都必須在 YOLO 之外加入 MediaPipe、時間追蹤或球場座標轉換。

## 研究 1：持拍手判定

### 想回答的問題

畫面中的球拍比較靠近左手腕還是右手腕？

### 處理流程

`影片 → MediaPipe 左右手腕 → YOLO 球拍框 → 距離/重疊配對 → 左手或右手`

### 要收什麼資料

- PoC 起步：500–1,000 張有清楚球拍的影格。
- 至少 30 位球員，左右手持拍都要有，避免模型只記住某個人。
- 包含正面、側面、背面、遮擋、深色/亮色球拍、不同場館光線。
- 同一支影片的影格只能放在 train、validation、test 其中一組；最好依球員切分，防止「看過同一個人」造成假高分。

### 要標註什麼

- `racket` bounding box。
- 測試集額外標註 `racket_hand = left/right/uncertain`，供最終判定評分。
- 手腕位置可由 MediaPipe 產生，不需全靠人工畫框。

### 怎麼訓練

1. 先只訓練單類別 `racket`。
2. 先用 640 或 960 輸入尺寸比較小球拍/細球拍的召回率。
3. 取得球拍框中心，和 MediaPipe 左右手腕距離比較。
4. 加入「太遠或被遮擋就回傳 uncertain」，不要強迫猜左右手。

### 看哪些數字

- 球拍 detection mAP50-95。
- 球拍 recall：真正有球拍的畫面有多少被找出。
- 左右手判定 accuracy。
- uncertain 覆蓋率與錯判率。

PoC 可先設定內部目標：held-out 球員的球拍 mAP50 ≥ 0.70、可判定畫面的左右手 accuracy ≥ 90%。這是專案閘門，不是本輪已達成的數字。

### 與目前功能的關係

現有 MediaPipe 已能用雙手腕路徑估計 active/dominant hand，但不看球拍。此研究的價值是提供「真的看到球拍靠近哪一手」的第二份證據，而不是把既有結果全部推翻。

## 研究 2：羽球路徑

### 想回答的問題

羽球從哪裡飛到哪裡？軌跡是否連續？

### 為什麼比球拍難

羽球在畫面中很小、速度快、容易模糊、會被燈光與白線混淆。30 FPS 手機影片常在相鄰影格之間移動很遠，甚至完全消失。

### 建議拍攝條件

- 優先 1080p、120 FPS；至少比較 60 FPS 與 120 FPS。
- 固定相機、短曝光、能看見完整飛行範圍。
- 收集近端/遠端、網前/後場、高球/殺球等不同尺度與速度。

### 要收什麼資料

- PoC 起步：100 段短球路、約 5,000–10,000 張經挑選的標註影格。
- 包含「羽球可見」「動態模糊」「被遮擋」「完全不可見」狀態。
- 依完整 rally 或拍攝場次切分 train/validation/test，不能把相鄰影格拆到不同組。

### 要標註什麼

- 每一個可見羽球的 bounding box；若只有幾個像素，可改標中心點並在訓練前轉為固定小框。
- `visibility = clear/blurred/occluded/not_visible`。
- 每段軌跡的 `track_id`。

### 怎麼訓練與追蹤

1. 訓練 `shuttlecock` 單類別 detector，先比較 640、960、1280 尺寸。
2. 必要時將全畫面切片推論，避免縮圖後羽球只剩 1–2 pixels。
3. 把逐幀偵測交給 Kalman filter、ByteTrack 類方法或羽球專用時間模型連線。
4. 使用速度上限與拋物線/連續性規則去掉燈光、白線等誤判。

### 看哪些數字

- visible frames 的 detection recall。
- 中心點 median pixel error。
- false positives / 每分鐘。
- track completeness：一整段可見軌跡有多少比例被連續追蹤。
- longest gap：最長中斷幀數。

PoC 可先把 visible-frame recall ≥ 80%、median 中心誤差 ≤ 10 pixels、每段軌跡覆蓋 ≥ 70% 設為研究目標；必須依原始解析度再校準。

## 研究 3：羽球落點分析

### 想回答的問題

羽球落在球場哪裡？距離標準位置多遠？屬於哪一個區域？

### 必要流程

`球場角點/線 → homography 座標校正 → 羽球軌跡 → 落地事件 → 影像點轉球場座標`

YOLO 只能幫忙找羽球或球場物件，不能單獨完成以上所有步驟。

### 要收什麼資料

- PoC 起步：至少 300–500 個有明確落地畫面的球。
- 前場、中場、後場、左右區域要平衡。
- 固定相機版本先做；移動相機是另一個難度等級。
- 最好在場地放可量測標記，讓人工落點有公分基準。

### 要標註什麼

- 球場四角與關鍵線交點，或使用固定相機的一次性校正檔。
- 每球的 `landing_frame`。
- 落點 `x, y`（球場座標）與區域名稱。
- 落地不可見或有爭議時標為 `uncertain`，不能硬猜。

### 怎麼做

1. 先完成研究 2 的羽球軌跡。
2. 用球場角點建立 homography，將影像座標映射到標準球場平面。
3. 用垂直速度反轉、軌跡停止/反彈、相鄰幀位置與人工落地幀訓練時間事件模型。
4. 將落地點轉成公分與前/中/後、左/右區域。
5. 對 `uncertain` 個案交由人工確認。

### 看哪些數字

- landing event frame error。
- 落點 median / P90 距離誤差（公分）。
- 區域分類 accuracy 與 confusion matrix。
- 系統可判定率：有多少球能給出非 uncertain 結果。

PoC 可先設定固定相機下 median 落點誤差 ≤ 30 cm、區域 accuracy ≥ 85% 為內部目標。正式門檻要依教學用途與人工標註誤差重新決定。

## 建議執行順序

1. **先做持拍手**：物件較大、能直接與現有 MediaPipe 融合，最快得到有意義的結果。
2. **再做球路徑**：先改善拍攝條件與標註流程，再談模型。
3. **最後做落點**：它依賴穩定球路與球場校正，不能跳步。

## 每個研究都要保留的證據

- 資料版本、影片與球員數、各 split 數量。
- 標註規範與至少 20 張人工抽查畫面。
- 固定的 test set，不能為了結果好看一直換。
- 訓練設定、來源 commit、模型檔 hash、耗時與硬體。
- precision、recall、mAP 之外的任務指標。
- 成功與失敗畫面各一組，特別保留遮擋、模糊與小物件案例。
- 明確寫出哪些是實測、哪些是目標、哪些尚未測得。
